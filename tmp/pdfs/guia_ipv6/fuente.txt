Introducción 
 
El presente documento evidencia la implementación de una infraestructura virtualizada 
compuesta por un cliente Ubuntu Desktop y dos servidores Fedora Linux y FreeBSD. Los 
tres equipos fueron conectados mediante una red interna de VirtualBox y configurados 
con direccionamiento IPv6 estático dentro del prefijo 2001:db8:1::/64. 
 
Posterior a verificar la comunicación entre los sistemas, se configuró el servicio SSH en 
los servidores Fedora Linux y FreeBSD utilizando el puerto TCP 3625. Asimismo, se 
realizaron pruebas de conectividad y acceso remoto desde Ubuntu Desktop, con el 
propósito de co mprobar el funcionamiento de la red y aplicar prácticas básicas de 
administración remota y seguridad.  

PAGINA 4
2 
 
Objetivos 
 
General: 
Implementar una infraestructura virtual con direccionamiento IPv6 que permita la 
comunicación entre Ubuntu Desktop, Fedora Linux y FreeBSD, y la administración remota 
de los servidores mediante SSH en el puerto 3625. 
 
Específicos: 
• Crear y configurar tres máquinas virtuales en una misma red interna. 
• Asignar direcciones IPv6 estáticas dentro de una misma subred. 
• Validar el acceso remoto desde Ubuntu Desktop hacia ambos servidores. 
• Habilitar el acceso SSH desde Ubuntu Desktop hacia Fedora Linux y FreeBSD 
mediante cuentas de usuario y el puerto TCP 3625. 
• Documentar los comandos, resultados y buenas prácticas aplicadas.

Diseño de la infraestructura virtual 
Como primer punto, utilizamos Oracle VM VirtualBox para crear tres equipos con 
funciones diferenciadas. Ubuntu Desktop actúa como estación  de administración, 
mientras Fedora Linux y FreeBSD ofrecen el acceso remoto al servicio SSH. 
VirtualBox proporciona el entorno de ejecución y el enlace virtual compartido.  
Equipo Sistema y función Interfaz Rol Red  
Ubuntu_Cliente Ubuntu Desktop; cliente SSH enp0s3 Cliente Desktop desafio2 
Fedora_Server Fedora Linux; servidor SSH enp0s3 Servidor Linux desafio2 
FreeBSD_Server FreeBSD; servidor SSH em0 Servidor BSD desafio2 
 
Creación de Ubuntu Cliente 
Se creó una máquina virtual para Ubuntu Desktop, que funcionará como cliente de 
administración. En el asistente se define el nombre de la máquina, la ubicación de sus 
archivos, la imagen de instalación y el tipo de sistema operativo. Estos datos permiten 
identificar el equipo y arrancar el instalador adecuado. 
Nota: La memoria RAM y los procesadores virtuales determinan los recursos disponibles 
para el sistema invitado. Deben ser suficientes para ejecutar el escritorio y la terminal sin 
agotar los recursos del equipo anfitrión. La creación de la máquina todavía no configura 
su dirección IPv6 ni habilita SSH.

Plan de direccionamiento IPV6 
Equipo Dirección IPv6 Prefijo 
Ubuntu_Cliente 2001:db8:1::10 /64 
Fedora_Server 2001:db8:1::20 /64 
FreeBSD_Server 2001:db8:1::30 /64 
 
En Ubuntu se abrió la configuración de red, luego se seleccionó el método Manual para 
IPv6 y se asignó 2001:db8:1::10 con prefijo 64. Se dejó vacía la puerta de enlace porque 
la comunicación ocurre dentro del mismo enlace y subred. 
 
Figura 12. Asignación manual de IPv6 en la interfaz gráfica de Ubuntu 
Las tres direcciones comparten los primeros 64 bits de red y difieren en la identificación 
del equipo.  
El bloque 2001:db8::/32 está reservado para documentación; se conserva en este 
escenario aislado, pero no debe utilizarse como direccionamiento público real ni 
confundirse con un prefijo privado de producción (Huston et al., 2004).

Configuración IPv6 de Fedora 
Se utilizó ip link para identificar la interfaz de red. En este equipo corresponde a enp0s3. 
Luego se creó un perfil de NetworkManager llamado IPv6-lab, se asignó la dirección 
estática y se activó la conexión. 
ip link 
sudo nmcli connection add type ethernet ifname enp0s3 \ 
 con-name "ipv6-lab" ipv6.method manual \ 
ipv6.addresses 2001:db8:1::20/64 
sudo nmcli connection up "ipv6-lab" 
ip -6 addr show dev enp0s3

Servicio SSH en Fedora Linux 
Configuramos el servidor OpenSSH para recibir conexiones en el puerto 3625.  
En /etc/ssh/sshd_config se estableció la directiva Port 3625 y se reinició sshd. La 
directiva define el puerto de escucha del servidor; el cliente debe seleccionar el mismo 
puerto al iniciar la conexión (Canonical, s. f.). 
El comando sed registrado reemplaza la línea comentada #Port 22; la consulta posterior 
con grep permite observar la directiva escrita. Si el archivo tiene otro formato, ese 
reemplazo puede no producir el cambio esperado. 
sudo sed -i 's/#Port 22/Port 3625/' /etc/ssh/sshd_config 
sudo cat /etc/ssh/sshd_config | grep Port 
 
Figura 21. Modificación del puerto SSH de Fedora 
 
Figura 22. Operaciones sobre SELinux y el firewall. 
 
Figura 23.  Reinicio de sshd y verificación de escucha. 
Durante la prueba se ejecutó setenforce 0, que coloca temporalmente SELinux en modo 
permisivo. También se agregó una regla permanente para TCP 3625 con firewall-cmd, se 
recargó el firewall y se reinició sshd. El resultado success corresponde a la operación del 
firewall; no demuestra por sí solo que una conexión remota sea posible. 
sudo firewall-cmd --add-port=3625/tcp --permanent 
sudo firewall-cmd --reload 
sudo systemctl restart sshd 
La salida de escucha muestra el puerto 3625. Mantener SELinux permisivo es una 
limitación de seguridad: la solución definitiva debe autorizar el puerto y repetir el acceso 
con SELinux activo, como se explica en el análisis.

Acceso SSH desde Ubuntu hacia Fedora 
Desde Ubuntu Cliente se ejecutó SSH indicando el puerto 3625, el usuario fedoraserver y 
la dirección IPv6 del servidor Fedora. El cliente solicitó confirmar la clave del servidor y 
luego la contraseña de la cuenta remota. 
ssh -p 3625 fedoraserver@2001:db8:1::20 
 
Figura 24. Sesión SSH iniciada desde Ubuntu hacia Fedora en el puerto 3625. 
La secuencia termina en el prompt fedoraserver@localhost, lo que, junto con el comando 
de conexión y la autenticación, demuestra el acceso a Fedora.  
El cambio de texto del prompt por sí solo no basta: debe interpretarse con toda la 
secuencia mostrada. 
El aviso de clave desconocida aparece porque el cliente no tenía registrada la identidad 
del servidor. Se observa su aceptación, pero no una comparación independiente de la 
huella. Como buena práctica, la huella debe verificarse antes de aceptar una clave nueva. 
Con esta sesión se comprobó el acceso requerido desde Ubuntu a Fedora por TCP 3625.

Figura 32. Prueba de conectividad desde FreeBSD hacia Fedora. 
La prueba indica cuatro paquetes enviados, cuatro recibidos y 0,0 % de pérdida. El tiempo

deben comprobarse por separado.

Análisis de resultados 
Las evidencias confirman el direccionamiento de las tres máquinas y las dos conexiones 
SSH requeridas desde Ubuntu. Las pruebas ICMPv6 de FreeBSD hacia Fedora y de Ubuntu 
hacia FreeBSD no registraron pérdida de paquetes en los cuatro envíos de cada ensayo. 
Las sesiones SSH prueban una función distinta a ping: además de comunicación IP, 
requieren un servicio en escucha, permiso de acceso y autenticación del usuario. La 
consulta remota de ifconfig en FreeBSD permite relacionar la sesión con la configuración 
del equipo destino. 
Origen Destino Prueba Resultado 
Ubuntu ::10 Fedora ::20 SSH TCP/3625 Exitoso 
Ubuntu ::10 FreeBSD ::30 ICMPv6 + SSH TCP/3625 Exitoso 
FreeBSD ::30 Fedora ::20 ICMPv6 + SSH TCP/3625 Exitoso 
 
La configuración de Fedora incluye una regla del firewall, pero también el uso temporal 
de SELinux permisivo. Para mantener las protecciones activas, debe revisarse la 
asociación del puerto con el tipo ssh_port_t y repetirse el acceso con SELinux en Enforcing 
(Red Hat, 2025). Esta mejora no se presenta como ya ejecutada. 
getenforce 
sudo semanage port -l | grep ssh_port_t 
# Solo si el puerto aún no está registrado 
sudo semanage port -a -t ssh_port_t -p tcp 3625 
# Si SELinux está Permissive y la política ya está lista 
sudo setenforce 1 
sudo sshd -t 
sudo systemctl restart sshd 
Si semanage no está instalado, se requiere policycoreutils -python-utils. Si 3625 ya 
pertenece a otro tipo, debe revisarse su uso antes de cambiarlo. setenforce 1 no habilita 
un sistema que tenga SELinux completamente Disabled. También se debe comprobar que 
la regla TCP 3625 pertenece a la zona de la interfaz del laboratorio. 
Se recomienda evitar el inicio remoto directo de root, proteger las credenciales y verificar 
las huellas de los servidores. Cambiar el puerto no sustituye estas medidas.
